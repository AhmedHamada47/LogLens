LogLens: how an ASP.NET Core MVC web app became a Windows desktop app

A complete walkthrough of the LogLens project: every file, how the desktop icon, tray and installer work, how a 47 MB log is parsed in seconds, and every problem we hit on the way and how each one was solved.

.NET 9 · ASP.NET Core MVC SQLite WinForms tray icon Inno Setup installer GitHub Actions releases

The main idea

LogLens is a normal ASP.NET Core MVC website. It never needed to be rewritten as WPF or WinForms. The trick is to ship the web server and the website together inside one Windows program:

1 · A local web server

LogLens.exe starts Kestrel (ASP.NET Core's built-in web server) on http://127.0.0.1:5189. Only this computer can reach it.

2 · The browser is the window

When the server is ready, LogLens opens that address in the default browser. The browser draws the UI; the server does the work.

3 · A tray icon instead of a console

The exe is a Windows app (no black console). A tray icon lets you reopen the page or Exit.

4 · Everything bundled

The .NET runtime is packed in (self-contained), so users install nothing else. An installer adds the desktop icon.

Why this approach? All the existing MVC code (controllers, Razor views, CSS, JS) keeps working unchanged. We only added a thin "desktop shell" around it: windowed exe + tray + icon + installer.

What happens when you double-click the icon

All of this lives in Program.cs (plus Desktop/TrayIcon.cs), in this order:

  1. Single-instance check. A named Windows mutex LogLens_SingleInstance is created. If it already exists, LogLens is already running, so this second copy just opens the browser at the running server and exits. No duplicate servers, no port clash.
  2. Find the data folder. %LOCALAPPDATA%\LogLens is created if missing. The database file loglens.db lives there, so it survives updates and needs no admin rights.
  3. Set the content root to the install folder. ContentRootPath = AppContext.BaseDirectory makes ASP.NET look for wwwroot (CSS/JS) next to the exe, no matter how the app was launched. (Getting this wrong caused the "unstyled pages" bug; see challenges.)
  4. Start Kestrel on loopback only. options.Listen(IPAddress.Loopback, 5189). Other machines on the network cannot connect. Upload limits are raised to 500 MB.
  5. Prepare the database. EnsureCreated() builds the tables the first time. A small SchemaVersion table records upgrades (extra indexes, the CorrelationId column) so old databases are upgraded safely.
  6. Add security headers. CSP, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, plus anti-forgery tokens on every POST.
  7. Open the browser when the server reports "started" (ApplicationStarted).
  8. Show the tray icon on its own thread, with a "LogLens is running" balloon.
  9. Run. If startup fails (for example port 5189 is taken by another program), a Windows message box explains why, instead of failing silently.

The tray icon (Desktop/TrayIcon.cs)

Windows tray icons need a message loop on an STA thread. The web server already owns the main thread, so the tray runs on its own background thread:

var thread = new Thread(() => Run(lifetime, url, openBrowser)) { IsBackground = true };
thread.SetApartmentState(ApartmentState.STA);   // required by Windows UI components
thread.Start();
...
menu.Items.Add("Open LogLens", null, (_, _) => openBrowser(url));
menu.Items.Add("Exit", null, (_, _) => { icon.Visible = false; lifetime.StopApplication(); Application.ExitThread(); });
icon.DoubleClick += (_, _) => openBrowser(url);
Application.Run();                              // the tray's message loop

Exit asks ASP.NET to shut down cleanly (StopApplication), which ends app.Run() and the process. The icon image is read from the exe itself with Icon.ExtractAssociatedIcon, so there is only one icon file to maintain.

The icon: how it was made and where it is used

LogLens.ico was drawn by a small PowerShell script using System.Drawing: a rounded blue-to-teal square, three coloured "log level" dots with lines (green / yellow / red), and a magnifying glass. It was rendered at 16, 24, 32, 48, 64, 128 and 256 px and packed into one .ico file (each size stored as a PNG), so Windows always picks a sharp size for the desktop, taskbar, tray or Explorer.

The download link and how releases work

The permanent link that always downloads the newest published version:

https://github.com/AhmedHamada47/LogLens/releases/latest/download/LogLens-Setup.exe

It works because GitHub's /releases/latest/download/<file> always redirects to that file on the newest published (non-draft) release. The repo had to be public for anyone to download it.

The automated pipeline (.github/workflows/release.yml)

  1. You push a tag like v1.0.1.
  2. GitHub starts a fresh Windows machine, installs .NET 9, and runs the unit tests.
  3. dotnet publish builds the self-contained app.
  4. Inno Setup is installed (choco install innosetup) and compiles the installer with the version taken from the tag.
  5. The installer is attached to a draft release. Drafts are invisible to the public, so you can download and test it first.
  6. When you're happy, click Publish release on GitHub, and the public link starts serving the new version.

Indexes make filtering instant even with hundreds of thousands of rows: (SessionId, Timestamp), (SessionId, Level), (SessionId, CorrelationId), plus Timestamp and Level.

Where it lives: %LOCALAPPDATA%\LogLens\loglens.db. Uninstalling the app leaves your sessions; delete that folder to wipe them.

How a 47 MB log is parsed in seconds

47.5 MB
test file (fake data)
216,444
entries created
~4–7 s
upload + parse + save
0.3 s
to open the session page

Measured on this PC with a generated log in the same Serilog format as real TeoriBox logs. The speed comes from six choices working together:

1 · Stream, never load the whole file

ParseStreamEnumerable reads the upload with a 4 MB-buffered StreamReader, line by line, and yield returns each finished entry. Only one entry is in memory at a time, so a 500 MB file uses about as much RAM as a 1 MB file.

2 · Detect the format once

Four compiled regexes cover the supported formats:

2026-10-21 04:13:37.060 +02:00 [INF] [Source] [CorrelationId:abc] message   ← Serilog with time zone
2026-10-21 04:13:37 [Information] Source: message                           ← Serilog without zone
2026-10-21 04:13:37 ERROR Source - message                                   ← "standard"
[2026-10-21T04:13:37] [WARN] message                                         ← bracketed

For the first lines every pattern is tried. After 3 lines match the same pattern, that pattern is locked in and used alone. Other patterns are only tried again for the first 50 lines if a line fails. That's one regex per line instead of four.

3 · Multi-line entries handled in the same pass

A line that doesn't start with a timestamp belongs to the previous entry. Lines starting with at , --- or Exception are appended to StackTrace; anything else (like a long SQL statement) is appended to the message. Caps keep pathological files safe: ≤20 continuation lines, message ≤2,000 chars, raw line ≤500.

4 · Raw SQLite inserts in one transaction

EF Core is great for normal queries, but its change tracking is slow for 200k inserts. The upload uses plain ADO.NET instead:

await using var transaction = await conn.BeginTransactionAsync();   // ONE transaction for the whole file
insert.CommandText = "INSERT INTO LogEntries (...) VALUES ($ts, $lvl, ...)";
await insert.PrepareAsync();                                         // SQL compiled once
foreach (var entry in _parser.ParseStreamEnumerable(stream))
{
    pTs.Value = entry.Timestamp.ToString("o"); ...                   // only parameter values change
    await insert.ExecuteNonQueryAsync();
}
await transaction.CommitAsync();

Without the transaction, SQLite would flush to disk after every row: a few hundred rows per second instead of tens of thousands.

5 · SQLite tuned for bulk writes

PRAGMA journal_mode=WAL;      -- readers don't block the writer
PRAGMA synchronous=NORMAL;    -- fewer disk flushes, still safe in WAL mode
PRAGMA cache_size=-64000;     -- 64 MB page cache
PRAGMA temp_store=MEMORY;

6 · Heavy numbers computed by the database

The session page doesn't load rows to count them. Level counts, the top-10 errors and the per-minute timeline are single GROUP BY queries that use the indexes, which is why the page opens in ~0.3 s.

Showing 200,000+ rows without freezing the browser

Putting 216,444 table rows in a page would freeze any browser. The viewer uses virtual scrolling:

  1. On scroll, compute which row indexes are on screen: floor(scrollTop / rowHeight), plus a 20-row buffer each side.
  2. Find every 200-row block those indexes touch that isn't cached yet, and fetch all of them from EntriesApi.
  3. Draw a top spacer, the ~50 real rows, and a bottom spacer, so the scrollbar stays correct.
  4. When the fetched blocks arrive, draw again at the current scroll position.
  5. Measure the real row height (e.g. 33.4 px with Windows display scaling) and use it for all the math.

Exports (CSV/JSON) also stream row by row from the database to the download, so exporting everything never builds a giant string in memory.

Every challenge and how it was solved

1 · A black console window stayed open

Problem
ASP.NET apps are console apps by default. Users saw a console, and closing it killed the app.
Fix
OutputType=WinExe plus a tray icon (Desktop/TrayIcon.cs) with Open/Exit. Startup errors that used to print to the console now show a message box.

2 · WinForms and ASP.NET name clashes

Problem
Enabling WinForms adds global using System.Windows.Forms; and System.Drawing, whose types (Control, View, Timer…) can collide with MVC names.
Fix
<Using Remove="…" /> in the csproj; only TrayIcon.cs imports WinForms explicitly.

3 · No icon

Problem
The project had no .ico, and the installer's icon line was commented out.
Fix
Generated a multi-size LogLens.ico and wired it into the exe, installer, uninstall entry and tray (details).

4 · Pages showed up unstyled; buttons didn't work

Problem
ASP.NET looks for wwwroot in the current folder. When LogLens was started from anywhere else (the installer's "Launch" checkbox, another program, a script), every CSS/JS file returned 404. You saw plain blue links and no styling.
Fix
ContentRootPath = AppContext.BaseDirectory: always use the install folder. Verified by launching from an unrelated folder; all CSS/JS return 200.

5 · Upload stuck on "Processing…" for 5 minutes

Problem
It looked like slow parsing, but measurement showed the server handles 47 MB in ~4 s. The real cause had two parts: SessionName was a non-nullable string, which ASP.NET treats as required, so the browser silently blocked the upload ("The SessionName field is required"). Meanwhile the button switched to "Processing…" anyway and only reset after a hard-coded 300000 ms (5-minute) timer.
Fix
SessionName is string? (optional) and defaults to the file name. The spinner only shows when validation passes and a file or text is present. The 5-minute timer is gone, and the button resets on browser Back.

6 · Blank space in the log viewer

Problem
When the visible rows spanned two 200-row blocks (fast scrolling, or jumping to the end), the viewer fetched only one block, drew empty rows for the rest, and never redrew them. Also, it assumed rows were 32 px when they were really 33.4 px, so positions drifted.
Fix
Fetch every missing block in the visible range and re-render at the current scroll position when they arrive. Use the measured row height (kept separate from the drawn height, so it can't feed back into itself). Tested at 0%, 25%, 50%, 99%, the very bottom and after rapid random jumps: zero blank rows.

7 · Private log data in the git history

Problem
Before making the repo public, a scan found a deleted ~800 MB loglens.db in old commits, holding 721,313 real log entries. Deleted files remain downloadable from public history.
Fix
Local backup first (LogLens-backup-before-purge.git), then git filter-branch removed the database from every commit, garbage collection shrank the repo to under 1 MB, and main was force-pushed before the repo went public.

8 · Shipping before testing

Problem
The first release build published itself publicly before it could be tested; a cancel arrived seconds too late.
Fix
Turned it back into a draft immediately, and changed the workflow to draft: true. Every build now waits for a human to test and click Publish.

9 · Two copies fighting over one port

Problem
Double-clicking twice could start two servers on port 5189.
Fix
A named mutex: the second launch just opens the browser. The installer uses the same mutex name to ask you to close LogLens before upgrading.

10 · "Windows protected your PC"

Problem
Unsigned downloads trigger SmartScreen.
Fix
Documented the "More info → Run anyway" step in the README. A permanent fix needs code signing (below).

11 · Users need .NET installed

Problem
A normal .NET build needs the runtime on the target PC.
Fix
Self-contained win-x64 publish: the runtime ships inside the installer (~160 MB on disk, ~47 MB download thanks to LZMA2 compression).

How-to recipes

Run it while developing

dotnet run

Build the installer on your PC

winget install JRSoftware.InnoSetup   # once
publish.bat                            # → installer\output\LogLens-Setup.exe

Release a new version

git tag -a v1.0.1 -m "LogLens 1.0.1"
git push origin v1.0.1
# wait for the Release workflow → test the draft on GitHub → click "Publish release"

Change the port

Edit DefaultPort at the top of Program.cs (and Properties/launchSettings.json for development).

Change the icon

Replace LogLens.ico and rebuild (details).

Reset all data

Exit LogLens from the tray, then delete %LOCALAPPDATA%\LogLens.

Uninstall

Windows Settings → Apps → LogLens → Uninstall (your data folder is kept).
